# Профилирование и нагрузка

Цель: найти узкие места API и стрим-сервера, зафиксировать цифры «до» и повторить замер «после» кэширования теми же командами.

## Как повторить

Нужны Docker, [task](https://taskfile.dev), `hey` (`brew install hey`) и Go.

```bash
task bench -- baseline                      # микробенчмарки -> bench/results/baseline/micro.txt
task load:up                                # стенд: Postgres, app, stream; pprof на 127.0.0.1:6060 (app) и :6061 (stream)
task load:profile -- baseline channels      # GET /api/v1/channels
task load:profile -- baseline playback      # GET /api/v1/channels/1/playback
task load:profile -- baseline playlist      # плейлист на стрим-сервере по подписанной ссылке
task load:down
```

Второй аргумент `load:profile` задаёт имя набора (`baseline`, `cache` и т. д.), результаты лежат в `bench/results/<имя>/<сценарий>/`:

| Файл | Содержимое |
|---|---|
| `hey.txt` | RPS, задержки, распределение кодов ответа |
| `cpu.pprof`, `cpu.top.txt` | CPU-профиль за 20 с под нагрузкой и его топ |
| `allocs.pprof`, `allocs.top.txt` | аллокации за те же 20 с |
| `goroutine.txt` | снимок горутин |
| `pg.txt` | топ запросов из `pg_stat_statements` |
| `docker-stats.txt`, `meta.txt` | загрузка контейнеров, коммит, железо, параметры нагрузки |

Посмотреть профиль: `go tool pprof -http=:0 bench/results/baseline/channels/cpu.pprof`. Сравнить «до» и «после»: `go tool pprof -top -diff_base=bench/results/baseline/channels/cpu.pprof bench/results/cache/channels/cpu.pprof`, а микробенчмарки: `benchstat bench/results/baseline/micro.txt bench/results/cache/micro.txt`.

Параметры: `C` (параллелизм, по умолчанию 50), `DURATION` (30 с), `CPU_SECONDS` (20 с), например `C=100 task load:profile -- cache channels`.

Условия: закрытая нагрузка `hey` (каждый из 50 клиентов шлёт следующий запрос после ответа), пользователь `alice`, 30 каналов из seed. Контейнеры app и stream ограничены 2 CPU и 1 ГБ. Генератор нагрузки и стенд живут на одной машине, поэтому абсолютные числа годятся для сравнения «до/после» на этом же железе, но не как паспорт сервиса. Профили pprof не защищены авторизацией, стенд публикует их только на loopback.

## Результаты baseline (без кэша)

Коммит `f7d1d2c`, Apple M3 Pro, Docker Desktop, Go 1.27.2.

### Микробенчмарки (`micro.txt`, медианы из 3 прогонов)

| Бенчмарк | Время на операцию | Память на операцию |
|---|---|---|
| `passhash.Verify` (argon2id) | ~21 мс | 19,9 МБ, 28 аллокаций |
| `rest.Channels` (весь роутер, БД подменена, 4 слота хэша) | ~6,3 мс | 19,9 МБ, 81 аллокация |
| `streamserver.Playlist` (проверка подписи + подпись 6 сегментов) | ~9,2 мкс | 21,7 КБ, 203 аллокации |
| `stream.Sign` / `stream.VerifyLink` | ~0,87 / ~0,82 мкс | 1,5 / 1,2 КБ |

### Нагрузка (50 параллельных клиентов, 30 с)

| Сценарий | RPS | Средняя задержка | p99 | Ответы |
|---|---|---|---|---|
| `channels` | 87 | 572 мс | 782 мс | 200 |
| `playback` | 88 | 566 мс | 687 мс | 200 |
| `playlist` (стрим-сервер) | 20 867 | 2,4 мс | 23,5 мс | 200 |

### Узкие места

1. **argon2id на каждом запросе API (главное).** Basic Auth передаёт пароль в каждом запросе, и сервис заново считает хэш. В CPU-профиле `channels` и `playback` на `argon2.processBlockGeneric` и `blamkaGeneric` приходится около 95% времени, оба ядра заняты на 200%, а запрос к Postgres стоит 0,12 мс (`pg.txt`). Потолок ~87 RPS на 2 CPU, задержка почти вся в ожидании слота хэширования. Каждая проверка выделяет ~19,9 МБ (по 80 аллокаций на запрос, всё остальное ничтожно), отсюда давление на GC. Это ровно тот случай, ради которого нужен кэш успешных проверок.
2. **Подпись сегментов в плейлисте стрим-сервера.** На каждый запрос плейлиста `signSegments` заново подписывает все 6 сегментов: 24% CPU и 69% аллокаций (`allocs.top.txt`), из них HMAC (`hmac.New`) около 5% CPU. Плейлист меняется раз в ~2 с, а запрашивают его сотни зрителей, у каждого свой `uid` и срок, поэтому кэшировать нужно либо сам разобранный плейлист (подписывать только подписи), либо результат по ключу `(путь, uid, expires)`.
3. **Открытие файла плейлиста на каждый запрос.** `Transcoder.openPlaylist -> waitFile` делает `os.Open`, таймер и тикер на каждый запрос: ~11% CPU. Содержимое `index.m3u8` можно держать в памяти и обновлять по mtime.
4. Остальное: у стрим-сервера около трети CPU уходит на syscalls `net/http` (чтение и запись соединений). Это фон, оптимизировать здесь нечего.

Что не измерялось: стоимость самого ffmpeg (он работает в контейнере stream рядом с Go-кодом, поэтому загрузка контейнера в `docker-stats.txt` выше, чем в профиле Go) и раздача сегментов `.ts`: они живут ~12 с, ссылки на них меняются, и стабильную нагрузку на них эта схема не даёт.
