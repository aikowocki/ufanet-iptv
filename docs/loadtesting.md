# Профилирование и нагрузка

Цель: найти узкие места API и стрим-сервера, зафиксировать цифры «до» и повторить замер «после» кэширования теми же командами.

## Как повторить

Нужны Docker, [task](https://taskfile.dev), `hey` (`brew install hey`) и Go.

```bash
task bench -- baseline                      # микробенчмарки -> bench/results/baseline/micro.txt
task load:up                                # стенд: Postgres, app, stream; pprof на 127.0.0.1:6060 (app) и :6061 (stream)
task load:profile -- baseline channels      # GET /api/v1/channels
task load:profile -- baseline playback      # GET /api/v1/channels/1/playback
task load:profile -- baseline playlist      # плейлист на стрим-сервере по подписанной ссылке
task load:down
```

Второй аргумент `load:profile` задаёт имя набора (`baseline`, `cache` и т. д.), результаты лежат в `bench/results/<имя>/<сценарий>/`:

| Файл | Содержимое |
|---|---|
| `hey.txt` | RPS, задержки, распределение кодов ответа |
| `cpu.pprof`, `cpu.top.txt` | CPU-профиль за 20 с под нагрузкой и его топ |
| `allocs.pprof`, `allocs.top.txt` | аллокации за те же 20 с |
| `goroutine.txt` | снимок горутин |
| `pg.txt` | топ запросов из `pg_stat_statements` |
| `docker-stats.txt`, `meta.txt` | загрузка контейнеров, коммит, железо, параметры нагрузки |

Посмотреть профиль: `go tool pprof -http=:0 bench/results/baseline/channels/cpu.pprof`. Сравнить «до» и «после»: `go tool pprof -top -diff_base=bench/results/baseline/channels/cpu.pprof bench/results/cache/channels/cpu.pprof`, а микробенчмарки: `benchstat bench/results/baseline/micro.txt bench/results/cache/micro.txt`.

Параметры: `C` (параллелизм, по умолчанию 50), `DURATION` (30 с), `CPU_SECONDS` (20 с), например `C=100 task load:profile -- cache channels`.

Условия: закрытая нагрузка `hey` (каждый из 50 клиентов шлёт следующий запрос после ответа), пользователь `alice`, 30 каналов из seed. Контейнеры app и stream ограничены 2 CPU и 1 ГБ. Генератор нагрузки и стенд живут на одной машине, поэтому абсолютные числа годятся для сравнения «до/после» на этом же железе, но не как паспорт сервиса. Профили pprof не защищены авторизацией, стенд публикует их только на loopback.

## Результаты baseline (без кэша)

Коммит `f7d1d2c`, Apple M3 Pro, Docker Desktop, Go 1.27.2.

### Микробенчмарки (`micro.txt`, медианы из 3 прогонов)

| Бенчмарк | Время на операцию | Память на операцию |
|---|---|---|
| `passhash.Verify` (argon2id) | ~21 мс | 19,9 МБ, 28 аллокаций |
| `rest.Channels` (весь роутер, БД подменена, 4 слота хэша) | ~6,3 мс | 19,9 МБ, 81 аллокация |
| `streamserver.Playlist` (проверка подписи + подпись 6 сегментов) | ~9,2 мкс | 21,7 КБ, 203 аллокации |
| `stream.Sign` / `stream.VerifyLink` | ~0,87 / ~0,82 мкс | 1,5 / 1,2 КБ |

### Нагрузка (50 параллельных клиентов, 30 с)

| Сценарий | RPS | Средняя задержка | p99 | Ответы |
|---|---|---|---|---|
| `channels` | 87 | 572 мс | 782 мс | 200 |
| `playback` | 88 | 566 мс | 687 мс | 200 |
| `playlist` (стрим-сервер) | 20 867 | 2,4 мс | 23,5 мс | 200 |

### Узкие места

1. **argon2id на каждом запросе API (главное).** Basic Auth передаёт пароль в каждом запросе, и сервис заново считает хэш. В CPU-профиле `channels` и `playback` на `argon2.processBlockGeneric` и `blamkaGeneric` приходится около 95% времени, оба ядра заняты на 200%, а запрос к Postgres стоит 0,12 мс (`pg.txt`). Потолок ~87 RPS на 2 CPU, задержка почти вся в ожидании слота хэширования. Каждая проверка выделяет ~19,9 МБ (по 80 аллокаций на запрос, всё остальное ничтожно), отсюда давление на GC. Это ровно тот случай, ради которого нужен кэш успешных проверок.
2. **Подпись сегментов в плейлисте стрим-сервера.** На каждый запрос плейлиста `signSegments` заново подписывает все 6 сегментов: 24% CPU и 69% аллокаций (`allocs.top.txt`), из них HMAC (`hmac.New`) около 5% CPU. Плейлист меняется раз в ~2 с, а запрашивают его сотни зрителей, у каждого свой `uid` и срок, поэтому кэшировать нужно либо сам разобранный плейлист (подписывать только подписи), либо результат по ключу `(путь, uid, expires)`.
3. **Открытие файла плейлиста на каждый запрос.** `Transcoder.openPlaylist -> waitFile` делает `os.Open`, таймер и тикер на каждый запрос: ~11% CPU. Содержимое `index.m3u8` можно держать в памяти и обновлять по mtime.
4. Остальное: у стрим-сервера около трети CPU уходит на syscalls `net/http` (чтение и запись соединений). Это фон, оптимизировать здесь нечего.

Что не измерялось: стоимость самого ffmpeg (он работает в контейнере stream рядом с Go-кодом, поэтому загрузка контейнера в `docker-stats.txt` выше, чем в профиле Go) и раздача сегментов `.ts`: они живут ~12 с, ссылки на них меняются, и стабильную нагрузку на них эта схема не даёт.

## Итоги оптимизации

Ветка `task-4-optimization`. Наборы результатов: `baseline` (до правок), `cache` (шаги 1 и 2), `catalog` (шаг 3, все три шага). Железо, лимиты стенда и параметры нагрузки одинаковы, каждый сценарий снят один раз. Первый прогон `catalog` пришёлся на разряжающийся ноутбук и загруженную машину, поэтому набор снят заново от сети; в таблице ниже его результаты. Фоновая нагрузка на машине всё равно не нулевая, так что разброс у сценариев, код которых не менялся, возможен в пределах 10-20%.

### Что сделано

| Шаг | Изменение | Где |
|---|---|---|
| 1 | Кэш успешных проверок пароля: ключ `HMAC(секрет процесса, login:password)`, TTL `AUTH_CACHE_TTL` (45 с), `singleflight`, кэшируются только успехи. Смена пароля, выключение пользователя и смена роли в admin API сбрасывают записи пользователя сразу | `internal/usecase/auth/cached.go`, `internal/infra/cache/ttl.go`, `admin.WithUserInvalidator` |
| 2 | Стрим-сервер: плейлист читается из файла не чаще раза в 250 мс; подписанный плейлист кэшируется по `(путь, uid, expires, версия плейлиста)`, подпись входящей ссылки проверяется до кэша | `internal/streamserver/transcoder.go`, `streamserver.go` |
| 3 | Кэш списка каналов по `user_id`: запись живёт не дольше `CACHE_TTL` (10 с) и не дольше ближайшего `expires_at` подписки пользователя (читается отдельным запросом до списка). Любое изменение каналов, пакетов, состава и подписок в admin API сбрасывает кэш целиком | `internal/usecase/catalog/cached.go`, `ChannelRepository.NextSubscriptionExpiry`, `admin.WithCatalogInvalidator` |

Для каждого кэша есть тесты: попадание и промах, TTL, схлопывание параллельных промахов, неудачи не кэшируются, сброс при изменениях (включая сброс во время выполняющегося запроса), для плейлиста отдельно: чужие подписи не отдаются, просроченная ссылка даёт 403 при закэшированном плейлисте, новая версия плейлиста подписывается заново. SQL ближайшего срока подписки проверен интеграционным тестом на Postgres.

### Много пользователей и холодный старт

Сценарий `bench/multiuser.sh` (`task load:multiuser -- <метка>`): 200 разных пользователей из admin API (каждый с подпиской на пакет 1), 50 параллельных клиентов, каждый запрос идёт от случайного пользователя. Сначала перезапускается app (кэши пусты) и сразу даётся 15 с нагрузки (`cold`), затем ещё 15 с на прогретом кэше (`steady`). Результаты: `bench/results/multiuser-baseline/` (коммит `e748b53`, без кэшей) и `bench/results/multiuser-cache/` (текущая ветка).

| | baseline | после, холодный старт (15 с) | после, прогрето |
|---|---|---|---|
| RPS | 87 (75 во втором проходе) | 18 564 | 22 196 |
| Средняя / p99 | 588 / 796 мс | 2,7 / 8,7 мс | 2,3 / 7,1 мс |
| Ответы | только 200 | только 200 | только 200 |

Динамика холодного старта: за первые две секунды сервис отдаёт 180 и 408 запросов (каждый новый пользователь один раз платит за argon2id, 200 хэшей на 2 CPU занимают около двух секунд, p99 ~450-580 мс), с третьей секунды выходит на 16-24 тыс. RPS. 503 нет: очередь на хэширование короче `HASH_WAIT_TIMEOUT` (2 с). Без кэша те же 200 пользователей дают стабильные ~87 RPS всё время, потому что argon2id платится на каждый запрос.

Не покрыто: 15 с короче `AUTH_CACHE_TTL` (45 с), поэтому повторное протухание кэша паролей в прогон не попало. После него все 200 пользователей снова пойдут через argon2id одновременно, и на длинном прогоне (60 с и больше) будет видна такая же двухсекундная яма раз в 45 с. 200 пользователей это модель, а не размер реальной базы: при миллионе абонентов доля холодных запросов будет выше.

### Как менялись узкие места

- **argon2id на каждом запросе** (95% CPU, потолок ~87 RPS) исчез из профиля после шага 1.
- **`signSegments` и `os.Open` на стрим-сервере** (24% CPU и 69% аллокаций) ушли из топа после шага 2.
- **Запрос списка каналов в Postgres** после шага 1 занимал 42% CPU приложения, а Postgres был загружен на ~330%. После шага 3 запрос в профиле не виден: за 30 с под нагрузкой в `pg_stat_statements` 3 вызова вместо 336 тысяч, контейнер Postgres простаивает (2%).
- Теперь `channels` упирается в сам сервис: JSON-кодирование ответа (~27% CPU), запись в сокет (syscalls, ~30%). Дальше оптимизировать можно только отдавать готовый JSON из кэша, но выигрыш будет в пределах десятков процентов, поэтому остановились. У `playlist` остаются `net/http` и проверка подписи входящей ссылки (~10% CPU), которую кэшировать нельзя.

### Компромиссы и ограничения

- **Несколько экземпляров.** Кэши локальны, но правки админа доходят до всех экземпляров через `LISTEN/NOTIFY` (`pg_notify` в той же транзакции, что и запись; слушатель с переподключением и полным сбросом кэшей после каждого подключения). `bench/demo-invalidation.sh` поднимает два экземпляра: выключенная подписка видна на втором в списке каналов через ~20 мс вместо `CACHE_TTL` (10 с), выключенный пользователь получает 401 через ~40 мс вместо `AUTH_CACHE_TTL` (45 с). TTL остаётся страховкой на случай потерянного события. Нужно прямое соединение с Postgres: через PgBouncer в transaction-режиме `LISTEN` не работает. Нагрузочные замеры с уведомлениями не повторялись: админские правки не лежат на горячем пути, а слушатель добавляет одно соединение на экземпляр.
- **Сроки подписок.** Срок записи каталога считается относительно часов БД (разница `expires_at - now()` вычисляется в SQL), поэтому расхождение часов сервиса и БД не влияет.
- **Один пользователь в основных сценариях.** `channels`, `playback` и `playlist` идут под `alice`, поэтому кэши дают почти 100% попаданий. Многопользовательский сценарий и холодный старт разобраны выше; повторное протухание кэша через 45 с на длинной нагрузке не измерялось.
- **Отключить кэш нельзя**: `AUTH_CACHE_TTL` и `CACHE_TTL` принимают только положительные значения. Для отладки можно поставить `1ms`.
- Один прогон на сценарий и общая машина для стенда и генератора: числа пригодны для сравнения «до/после» на этом железе, но не как паспорт сервиса.

### Как повторить итоговый замер

```bash
git switch task-4-optimization
task bench -- catalog
task load:up
task load:profile -- catalog channels
task load:profile -- catalog playback
task load:profile -- catalog playlist
task load:down
```

Сравнение с baseline: `benchstat bench/results/baseline/micro.txt bench/results/catalog/micro.txt` и `go tool pprof -top -diff_base=bench/results/baseline/channels/cpu.pprof bench/results/catalog/channels/cpu.pprof`.
